## Design Specificity Verdict

**Mixed — real authored assets wrapped in the industry's most default container.**

**LLM assessment (Assessment A):** The macro-structure of nearly every page is the textbook AI-landing-page skeleton: hero = kicker + huge serif headline + lede + two buttons + decorative right-side visual; every listing page (guides/troubleshooting/compare) = kicker + h1 + subhead + a grid of identically-shaped cards; every card = kicker + title + one paragraph + optional meta line. Strip the copy and the DOM/CSS needs zero changes to become a project-management SaaS or an AI writing tool. That is the generic pattern the site's own brand positioning explicitly rejects ("not a lifestyle marketer, generic blogger, or AI-content site").

Against that, two things genuinely could not be dropped onto an unrelated product: the hand-built six-armed ice-crystal canvas on the homepage (`public/hero-sublimation.js`), which visualizes the actual sublimation physics the brand is named after, and the Batch Log tool's field set (water activity `aw`, 24-hour seal check, cost-per-bag), which only makes sense for someone who freeze-dries food for sale. The frost-blue/amber/warm-paper palette and serif display type are also a deliberate departure from default SaaS-blue-on-white.

**Verdict:** you built one good custom asset (the crystal) and one good custom feature (the tool), then wrapped both — and everything else — in the same card-grid template vocabulary the rest of the industry reaches for by default.

**Deterministic scan (Assessment B):** `detect.mjs` returned **zero findings** across `src/pages`, `src/components`, `src/layouts`, and `base.css` — confirmed as a genuine result (sanity-checked against a synthetic file that correctly triggered `overused-font`), not a scan failure, though `.astro`/`.css` scan in a weaker regex mode without full DOM/cascade resolution.

The **browser overlay** (a second, DOM-aware detector pass run live via script injection) told a different story than the static scan: it fired on 5 of 6 sampled pages, flagging `kicker-above-heading`, `tight-leading`, `cream-palette`, and `overused-font: Roboto`. Cross-checking against source: the `overused-font: Roboto` finding is a **false positive** — the codebase never declares Roboto; `--font-sans: system-ui, -apple-system, "Segoe UI", Roboto, Helvetica, Arial, sans-serif` is a system-font stack, and the headless browser's `system-ui` happened to resolve to Roboto in that environment. `edge-flush-cards` on the article page is also a **false positive** — it's an intentional horizontal-scroll fade on a wide comparison table (`.table-scroll` with an inset box-shadow), not misaligned cards. The `kicker-above-heading` finding, however, is a confirmed **true positive at the source level**: `guides.astro`, `troubleshooting.astro`, and `compare.astro` each render `<span class="kicker">` + heading + paragraph + optional meta line as the entry shape for three structurally different content types (long-form guides, symptom triage, spec comparisons), with `troubleshooting.astro` going as far as hardcoding the literal string "Symptom" identically on every card regardless of which symptom it is.

Both assessments converge on the same conclusion from two different angles — an LLM design review and a DOM-level automated scan — which is unusually strong agreement: **the card-grid/kicker pattern is real, site-wide, and content-blind**, even though the file-level regex scan alone would have missed it entirely.

## Overall Impression

This is a site that did the hard, specific work in exactly two places — the sublimation-crystal hero animation and the Batch Log's domain-accurate field set — and then let the rest of the interface default to the most generic container the industry produces. The copy has clearly internalized "don't sound like AI slop"; the UI hasn't yet been held to the same standard. The single biggest opportunity is giving the three content pillars (guides, troubleshooting, comparisons) visually distinct card grammars that match how each type of content actually works, instead of one reskin of `.card` doing all three jobs.

## What's Working

1. **The sublimation-crystal hero canvas** — hand-built six-armed crystal geometry with branch generation and drifting vapor particles, conceptually tied to the brand's own namesake (ice to vapor without a liquid stage). Not a stock particle/Lottie effect; it's the one piece of UI a competitor could not paste onto their own site unchanged.
2. **Batch Log's field vocabulary** — water activity (`aw`), 24-hour seal check, cost-per-bag math. These encode real cottage-food-safety practice (0.85 water activity is the actual regulatory threshold the site's own copy cites), not a generic "tracker" template's field set.
3. **A genuinely custom design-token system** — confirmed by both assessments: `--paper`, `--frost`, `--frost-deep`, `--amber` and `color-mix()`-derived tones instead of Tailwind/Bootstrap defaults, a single `--radius` token used everywhere instead of scattered ad hoc values, and a real serif display face (Iowan Old Style/Palatino) rather than system-sans-everywhere.

## Priority Issues

**[P1] One card shape serves three unrelated content types.** `guides.astro`, `troubleshooting.astro`, and `compare.astro` all render entries as the identical kicker + heading + paragraph `.card` (confirmed at the exact markup level by both assessments; `troubleshooting.astro` hardcodes the literal word "Symptom" on every card regardless of the actual symptom). A spec comparison of three machines gets the same box as a symptom-triage entry and a long-form guide teaser, with no versus/table affordance and no severity/diagnostic cue. *Why it matters:* this is the clearest, most reproducible signal that the UI was assembled top-down from a generic template rather than from what each content type actually needs — precisely the pattern the site's own copy rejects for itself. *Fix:* give `/compare` cards a distinct grammar (a small side-by-side spec preview or a "3 brands compared" chip) and troubleshooting cards a severity/likelihood cue, so the three pillars read as different kinds of content on sight. *Suggested command:* `/impeccable layout`

**[P1] Scroll-reveal-on-every-card-grid is itself a generic template motion signature, and it hides real content.** The `sp-card-reveal` animation applies uniformly to every `.card-grid` site-wide. Verified live: the homepage's "Flagship guides," "Fix this batch," and "Comparisons" sections, and troubleshooting's "After the batch" section, render fully transparent until the browser scrolls each grid into view. *Why it matters:* fade-up-on-scroll for every card grid is one of the most recognizable Squarespace/Webflow/Framer defaults, applied here with no variation by content, and it's a real content-visibility risk for anything that doesn't scroll incrementally (print, reader modes, some capture tools). *Fix:* reserve entrance motion for the hero/first fold, where it's paired with the bespoke crystal, and let listing-page cards render immediately. *Suggested command:* `/impeccable quieter`

**[P2] Generic hero shape.** Kicker + massive serif h1 + lede + two-button row + decorative right-side visual is the default AI-landing-page template. The crystal partially rescues it, but the two-button pattern and layout are otherwise interchangeable with any SaaS hero — the least differentiated moment on the page relative to the brand's "not a generic AI-content site" positioning. *Fix:* let the hero visual do more than decorate (tie it to something functional), or break the two-button/right-graphic convention outright. *Suggested command:* `/impeccable bolder`

**[P2] The kicker is a site-wide reflex, and it's inconsistently specific.** Listing cards use real taxonomy ("machines," "cottage business," "Symptom"), but the article page itself renders a generic pillar label ("GUIDE") in the same slot. *Why it matters:* if the eyebrow is meant to carry real information, it should say the same specific thing everywhere the content appears, not degrade to a category label once you land on the page. *Fix:* carry the specific taxonomy term through to the article header instead of the generic pillar name. *Suggested command:* `/impeccable clarify`

**[P3] Mobile header has no collapse.** Six nav items wrap to two full lines under the logo at 390px with no menu toggle, pushing the hero further down before any content is visible — a basic responsive-nav pattern most templates get right by default, so its absence here reads as a regression rather than a stylistic choice. *Fix:* collapse nav behind a toggle below ~640px. *Suggested command:* `/impeccable adapt`

## Persona Red Flags

**Casey (mobile):** Hits two problems back to back — the nav wraps to 2 lines with no collapse, and the hero visual is CSS-ordered above the headline at 620px and below, so before Casey reads a single word of "Home freeze-drying, batch by batch" they scroll past a decorative snowflake and a two-row nav bar.

**Jordan (first-timer):** Landing directly on `/troubleshooting` from search, a fast scroll or in-page jump can leave the "After the batch" card grid fully transparent (the scroll-reveal bug above) — a first-timer skimming the page could miss that rehydration/storage-failure guides exist at all.

**Alex (repeat cottage seller / power user):** No search or filter across guides/troubleshooting as the library grows, and the Batch Log has no per-food grouping or history view beyond a flat table — someone logging many batches over months can't see "my Skittles batches" as a set.

## Minor Observations

- Scrollbar theming and `::selection` color are low-cost bespoke touches most sites skip — a genuine point in the "not default" column.
- Article-page FAQ blocks (`notice-info`) are visually identical to the `EducationalNotice` safety-risk component; worth confirming these are meant to look the same, since one is a food-safety flag and the other is supplementary Q&A.
- No emoji/unicode glyphs anywhere in the source (confirmed by grep) — icons are either the one hand-authored SVG logo mark or absent, which is correct discipline rather than a gap.
- The `/compare` card's flex-row layout (kicker as a narrow left rail) is a mild variant of `.card` but not different enough to read as a distinct comparison-specific pattern — it's the closest thing to Priority Issue #1 already being partially addressed.

## Questions to Consider

1. If the brand's entire premise is "ice to vapor, no soggy middle," why does that idea live in exactly one canvas element on the homepage and nowhere else in the interaction language?
2. The Batch Log is the one page where users do something rather than read something; why does it visually blend into the same card/panel vocabulary as the read-only pages instead of having its own "workbench" register?
3. What would `/compare` look like if it were designed from the comparison first, a real side-by-side spec table as the primary object, rather than as a card that links out to one?
